# 附录 C 横向对比：OpenFGA / SpiceDB / Ory Keto / Casbin / OPA

> 说明：本书只运行和阅读了 OpenFGA。下面关于其他系统的内容来自它们的公开文档和设计，停留在**设计层面**，不涉及具体版本的功能细节和性能数字；选型前请以各项目当前的文档为准。

## C.1 两类系统

授权系统大体可以分成两类：

- **关系型（Zanzibar 系）**：授权数据是“谁和什么有什么关系”的元组，规则描述关系怎样推导。服务端存储并索引这些元组，回答 Check、反向列举等查询。OpenFGA、SpiceDB、Ory Keto 属于这一类；
- **策略型**：授权数据是调用方在请求时提供（或预先推送）的属性和事实，规则是一段在这些数据上求值的程序。服务端（或库）不负责存储业务关系。OPA 和 Casbin 更接近这一类。

两类的根本差别在于**数据在哪里**：关系型系统自己持有授权数据，所以能回答“anne 能看哪些文档”；策略型系统只看到请求里的数据，回答“这一次请求是否允许”很自然，回答“哪些对象允许”则需要把全部候选数据交给它。

## C.2 对比表

| | OpenFGA | SpiceDB | Ory Keto | Casbin | OPA |
|---|---|---|---|---|---|
| 形态 | 服务（gRPC + HTTP） | 服务（gRPC + HTTP 网关） | 服务（gRPC + REST） | 库（多语言实现） | 服务或库（Go），也可编译为 Wasm |
| 模型 | ReBAC，Zanzibar 风格的 DSL（类型、关系、重写规则） | ReBAC，schema 语言区分 relation 与 permission | ReBAC，Ory Permission Language（类 TypeScript 语法） | PERM 配置（request、policy、matchers、effect），可表达 ACL、RBAC、ABAC | 通用策略语言 Rego（受 Datalog 启发） |
| 授权数据 | 元组，存在 OpenFGA 的存储里 | 关系，存在 SpiceDB 的存储里 | 关系元组，存在 Keto 的存储里 | 策略行，通过适配器从文件或数据库加载 | 请求输入 + 预先加载的数据（bundle 等） |
| 属性 / 上下文 | 条件（CEL），参数来自元组和请求 | caveats（CEL），参数来自关系和请求 | 以关系为主 | matchers 里可以直接用请求属性 | 原生：规则就是在任意 JSON 上求值 |
| 反向查询 | ListObjects、ListUsers | LookupResources、LookupSubjects | 列举关系、展开 | 需要遍历策略 | 需要把候选集合作为输入 |

| 变更订阅 | ReadChanges（轮询） | Watch（流式） | — | — | — |
| 典型场景 | 应用内细粒度授权：文档、项目、组织层级 | 同左，强调一致性语义 | 同左，与 Ory 身份产品配合 | 单个应用内嵌的 RBAC/ABAC | 基础设施策略：Kubernetes 准入、API 网关、CI 规则 |

## C.3 和本书内容的对应

- **重写规则与集合运算**（第 4、10 章）：三个 Zanzibar 系系统都有并、交、差和“沿关系跳转”（OpenFGA 的 TTU，SpiceDB 的箭头 `->`），名字和语法不同，求值时面对的问题相同：环（第 12 章）、深度、扇出；
- **反向查询**（第 18–20 章）：关系型系统都需要“从用户出发”的索引和专门的算法；第 19 章讨论的交集和排除的难处是共同的；
- **一致性**（第 23 章）：Zanzibar 论文用 zookie 解决 new enemy problem；SpiceDB 把它作为一等概念（ZedToken）暴露给调用方，OpenFGA 提供的是更简单的“要么用缓存，要么 `HIGHER_CONSISTENCY`”；
- **属性**（第 14 章）：OpenFGA 和 SpiceDB 都选择了 CEL 作为关系之上的“条件”层，而不是把属性存进服务；OPA 和 Casbin 本来就以属性为中心；
- **正确性**（第 31 章）：本书对 OpenFGA 做的差分测试方法，同样适用于任何“重新实现”的授权引擎。

## C.4 怎么选

几个可以帮助判断的问题：

1. **授权数据本来就是关系吗？**（谁属于哪个团队、文档在哪个文件夹、谁是项目的成员）是的话，关系型系统省去了把这些数据同步到策略引擎里的工作，也能回答“我能看哪些”；
2. **需要“列出所有我有权限的对象”吗？**这是关系型系统的强项，策略型系统往往要配合应用自己的查询；
3. **规则主要依赖请求时的属性吗？**（时间、IP、请求的资源大小、Kubernetes 对象的字段）这是 OPA 的强项；
4. **只是一个应用内部的角色检查？**嵌入式的 Casbin 或者应用自己的代码可能就够了，不需要再运维一个服务；
5. **能接受的运维成本**：关系型系统是有状态的服务，要考虑存储、备份、迁移（第 21、22 章）、模型版本管理和一致性。

这些系统也常常组合使用：例如用 OPA 处理基础设施和网关层的策略，用 OpenFGA 或 SpiceDB 处理应用内部的资源授权。
